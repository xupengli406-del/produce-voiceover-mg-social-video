# 官方案例讲解：事实骨架与创作者叙事

当视频主题是官网实践、产品案例、帮助中心示例或官方操作文档时，官方文档是后台事实骨架，不是只挑几个亮点的素材池，也不是成片里反复朗读的主语。目标不是照读说明书或做“官网传话筒”，而是先把来源、证据和边界审清，再由创作者直接向观众讲明：案例解决什么、需要给什么、具体怎么做、为什么能做到、最后得到什么、哪里还要自己把关。

## 先做证据矩阵

写口播前，逐个案例建立下列八个必填字段。字段名保持一致，便于后续口播、时间轴和渲染计划互相核对；官网没有提供的信息要明确记为“未提供”，不能留空或靠推测补齐。

1. `available_options`：产品在这个任务里实际提供的可选路径、模式或组合，以及各自改变的变量。只列有官方依据或产品事实支持的选项。
2. `official_path`：官网这个具体案例实际选择并演示的路径。它是案例事实，不自动代表唯一解、默认最佳实践或创作者偏好。
3. `creator_preference`：创作者个人更愿意怎样使用，以及这种选择基于什么工作习惯或风险判断。没有真实亲测时只能表达选择与判断，不能声明取得了官网结果。
4. `selection_conditions`：什么条件下适合选择哪条路径，例如数据能否恢复、目录是否隔离、任务是否可信、是否需要人工检查点、连续执行是否更重要。
5. `steps`：按真实发生顺序记录输入、读取、规划、调用、确认、执行、回写和交付。每一步都必须能被观众跟着做，不能压缩成一句功能总结。
6. `image_evidence`：逐张写明图片来源、对应步骤、关键区域，以及它证明的是输入、动作、状态、接口返回、产物还是失败/空结果。
7. `result`：官网实际展示的文件、链接、状态、数据、会议、脚本或仅有方案，并注明结果来源。不要把“运行成功”自动解释成“数据完整”。
8. `limits`：权限、接口限制、服务不稳定、空结果、人工复核、未展示的后续动作和证据不能支持的结论。

任务与观众问题、输入与前置条件、产品机制仍需记录，可作为案例元信息或并入相关字段；不能用产品栏目名代替观众面对的具体麻烦。

多子流程案例必须分别填矩阵。不能因为它们共用一个实践标题，就把三条流程压成一句功能总结。

## 分清执行计划与权限模式

不要把“先预览再执行”和“默认权限/完全访问权限”写成同一件事。

- **任务执行计划**回答智能体按什么顺序工作：先给预览或计划、等待确认后执行，还是由智能体自主规划并连续推进。
- **产品权限模式**回答执行到文件写入、删除、脚本或外部程序等操作时，产品是否额外请求授权。
- 两个维度可以组合。开启完全访问仍然可以在提示词里要求先预览；希望连续执行时，默认权限也可能在高风险动作前暂停确认。

先在 `available_options` 中分别列清这两个维度，再在 `official_path` 中记录官网案例用了哪种组合，在 `creator_preference` 和 `selection_conditions` 中说明创作者会如何取舍。不得因为官网选择“先预览、后确认”就把它写成产品唯一能力、客观更优方案或创作者自己的结论；也不得为了突出创作者偏好而隐去官网对权限风险和适用条件的说明。

## 逐步声画绑定与渲染闸门

每个 `steps` 项必须绑定以下信息：

| 字段 | 必须回答的问题 |
| --- | --- |
| `narration_range` | 这一步在最终旁白中的实际开始和结束时码是什么？时码必须来自真实音频锚点。 |
| `visual` | 观众在这段时间看到哪张官网图、哪个完整界面或哪种明确标注的文字还原？ |
| `action` | 画面中发生什么可见动作，例如拖入、输入、点击、扫描、生成对照表、确认或回写？ |
| `result_state` | 动作结束后留下什么可验证状态，供观众确认这一步已经完成？ |

四项缺一，或图片无法支持当前口播，当前步骤即为 `blocked`。任何步骤仍为 `blocked` 时，不得批量渲染该系列；先补证据、改口播、重排画面，或明确官网未展示并使用有边界标签的文字还原。画面顺序默认遵循“全局定位 → 操作区域 → 动作发生 → 结果验证”，局部放大只在它能帮助验证当前步骤时使用。

## 口播顺序

全片先抓住零基础观众的信息缺口、好奇或焦虑，再给观看地图。每个案例内部默认按以下顺序组织：

1. 用人话说明这是什么案例、在解决什么。
2. 说清输入和前置条件。
3. 先交代可选路径和选择条件，再还原官网案例实际采用的路径；不要把示范路径说成唯一解。
4. 按真实旁白时段逐步推进，在对应步骤出现官网图片证据，并让画面动作和结果状态与口播同步。
5. 点出背后的产品机制。
6. 说明结果、交付物和官方证据能支持到什么程度。
7. 自然补上限制、风险或没跑通的部分。
8. 最后加入第一人称选择与判断，并把问题递到下一个案例。

创作者判断不得抢在案例理解之前。观众还不知道案例是什么、怎么跑，就直接说“我最喜欢这里”“它做得很好”，会让观点悬空。

第一人称来自查证、选择与使用立场，例如“我把这 11 个官方实践从头捋了一遍”“我更习惯把执行计划交给它”“碰到唯一副本时我会增加检查点”。它不能伪造亲测结果：只有实际运行并核验过产物，才能说“我跑过并得到”。只核对案例时，先在标题或开场建立一次来源背景；正文用“这个例子里”“这一次”“当时”“一般来说”等自然限定承接单次结果，不再每句重复“官网说”。禁止把单次案例结果改写成“我亲自跑下来得到”，也禁止为了避免假亲测而把整篇写成第三方资料播报。

## 资料来源与创作者表达分层

后台证据矩阵和成片口播承担不同任务，必须分开保存：

- 后台记录 `source_type`、`source_url`、`evidence_scope`、是否有图片、图片证明对象、未验证环节和视觉呈现方式。
- 成片只保留观众需要的任务、输入、动作、状态、结果、限制、选择条件和创作者判断。
- 来源背景通常在标题或开场交代一次即可。除非来源本身存在争议、版本冲突、广告合规或会直接改变可信度，否则正文不重复“官网说、官方表示、官网给了、官网演示”。
- 产品稳定能力可以直接说“它可以……”。单次案例结果用“这个例子里……”“这一次……”限定；历史接口或服务状态用“当时……”限定；经验性时长用“一般……，具体受……影响”表达，不能把单次样本升级成无条件承诺。
- 没有案例图片是制作信息，不是观众利益。直接把文字步骤做成 MG 流程，不在口播里说“官网没有图片”“我只能按文字还原”“视频里我会……”。若真正缺少的是结果证据，则把观众需要的边界说成人话，例如“这套流程说明它能这样安排，但最终质量仍要看实际交付”。
- 用户给出的个人工作流必须进入正文，而不是留在备注。进入前标记它属于产品原生能力、自定义连接器/机器人、外部工具、手动导入还是创作者人工调整，不能把组合用法冒充单一产品已经原生打通。
- 创作者可以直接说自己的结论，但结论必须有条件和对象。例如“我会先手动跑通再设自动化”，不写成“官网建议先手动跑通”；“它有两个典型场景”，不写成“官网给了两个场景”。

下列表达默认视为后台思维或传话筒语言，不得进入最终口播：

- “官网这部分只有文字说明/没有结果截图”；
- “所以视频里我会明确说这是按官网文字还原”；
- “这个实践官网没有案例图片，所以我只能……”；
- “官网说这次……”“官网给了两个场景”“官网的过程图里……”；
- “这能证明……但不能证明……”后接制作或取证过程，而不是观众能执行的判断。

改写时保留事实，不保留取证动作。例如：

- “官网说完整执行通常要两三分钟” → “这类完整执行一般要两三分钟，具体还会受内容量和网络影响。”
- “官网给了两个场景” → “它有两个典型场景。”
- “官网没有案例图，所以按文字流程讲” → 直接讲“手机发指令，电脑查文件或读日志，结果再回到手机”；画面改用 MG，不解释为什么没用截图。

## 图片与口播的证据关系

- 图片不是背景图。每张进入成片的官网图都要有一个明确的证明对象和对应口播。
- 优先保留完整上下文，再用框、遮罩、箭头或短标签指向关键区域；局部放大必须让观众更容易验证当前句子。
- 一个结果需要同时看成功项与排除范围时，不能裁掉其中一边。
- 官方截图出现报错、空数据、重试、等待或新旧链接差异时，必须保留并讲清，不能只截绿色成功状态。
- 官网没有配图时，使用 MG 流程动画、对象关系或状态变化来表达文字步骤；不能伪造官方 UI。是否需要屏幕来源标签取决于观众是否会把重绘误认成真实产品界面，但不得把“没有图片、按文字还原”朗读成口播。若文档也没有结果证据，只陈述流程和能力边界，不把结果说成已经实证完成。
- 配图重复且不增加信息时可不全部上屏，但矩阵中必须先分类，确认没有漏掉新的步骤、结果或边界。

## 媒体化改写，不机械念文档

官方逻辑要完整，官方句式不必保留。把说明书语言改成观众能跟住的因果链：为什么要做这一步、如果省掉会怎样、结果里哪一处真正有价值。用情绪和认知变化串联案例，但不能用情绪替代事实。

长清单可以按观众面对的问题分组，案例仍要保留最小完整链。某个案例如果必须用一句话带过，至少说清任务、关键机制、可验证结果和一个重要边界；不得只报功能名。

边界要像博主判断一样自然进入正文，不朗读“如图所示”“这张图证明”“画面为示意”“官网没有配图”等制作说明。屏幕若需要区分真实界面与重绘流程，可以使用不抢主体的来源标签；口播直接说观众需要的限制，例如“它能自己安排中间步骤，但最后的内容质量仍要检查来源和验收要求”。

## 两个验收测试

### 零基础复述测试

随机暂停到任一案例结束，观众应能复述：

- 它在解决什么；
- 要给它什么；
- 大致怎么做；
- 最后得到什么；
- 哪一步需要权限、确认或人工复核。

答不出来，说明案例还只是功能陈述。

### 证据边界测试

逐句标记为官方正文事实、官方图片证据、机制解释、创作者判断或未验证目标。任何一句结论都不得超过它的证据范围。尤其禁止：

- 把调用成功说成数据完整；
- 把脚本生成说成视频已经剪好并发布；
- 把新建链接说成原文档已原位修改；
- 把“尝试运行”说成所有环境一次成功；
- 把一次示例耗时说成稳定服务承诺。

## 样片先行

多案例系列先选择一个能覆盖“可选路径、官网路径、完整步骤、图片证据、结果、限制和创作者判断”的代表案例，制作约 30–60 秒完整结构样片。样片必须使用最终旁白或同等质量的定稿旁白，完成真实时码、逐步声画绑定、字幕、动效和 1× 播放检查。

样片未通过零基础复述、证据边界和逐步声画绑定检查前，不得批量渲染其余案例；可以继续核对事实矩阵和全稿，但不能把未验证的视觉模板扩散到整套视频。若上一版已因结构、证据或叙事失效被否决，必须重新通过这一闸门。
