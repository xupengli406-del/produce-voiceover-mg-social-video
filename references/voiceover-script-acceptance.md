# 口播稿精修与验收

写稿、改稿或在语音合成前验收最终口播时读取。目标不是产出一份“信息正确的说明文”，而是产出创作者真的会对观众说、零基础观众听得懂、每句都能进入画面的成片语言。

## 先分开后台稿与成片稿

后台资料可以包含来源链接、证据等级、截图缺失、文字还原、视觉方案、事实审计、未验证项和制作提醒。最终口播只能包含观众需要听到的内容。

| 后台需要记录 | 成片应该怎样说 |
| --- | --- |
| 来源来自官网案例 | 在标题或开场建立一次“本期拆官方实践”的背景，正文直接讲产品、动作和判断 |
| 某步骤只有文字、没有截图 | 直接讲步骤，用 MG 表达；不向观众解释为什么没上截图 |
| 单次案例得到 29 个文件/9 页 PPT | “这个例子里改了 29 个文件”“这一次交回来 9 页 PPT” |
| 截图只能证明调用成功 | “这一步跑通了，但返回的数据不一定完整” |
| 视觉要用文字还原 | 留在分镜或屏幕来源标签，不进入旁白 |
| 需要提醒不是亲测 | 不伪造“我跑出来”；同时避免每句重复“官网说”，改用“这个例子、这一次、当时” |

后台与成片必须是两个文件或两个明确字段。不得把事实审计、镜头说明或证据判断直接复制进口播。

## 创作者拥有最终叙述

资料进入内容后，产品事实、案例过程和创作者理解要变成一条由创作者讲给观众的完整叙事。除非来源本身会影响可信度或合规，来源主语只建立一次，不在正文反复出现。

优先使用：

- “它可以……”；
- “这个例子里……”；
- “这一次……”；
- “当时这个服务……”；
- “我会先……”；
- “我更看重……”；
- “一般要……，具体会受……影响”；
- “能做到 A，不等于已经保证 B”。

默认重写：

- “官网说/官网表示/官网提醒……”；
- “官网给了两个场景……”；
- “官网画面里可以看到……”；
- “官网这部分只有文字，没有截图……”；
- “所以视频里我会按文字还原……”；
- “这张图证明了……”；
- “我只能按它的流程来讲……”；
- “这能证明……但不能证明……”式取证报告语气。

“创作者拥有叙述”不等于伪造亲测。未实际运行时，不得说“我跑下来得到”“我让它处理后发现”。可以表达查证、理解、选择和使用方式；单次案例结果要用“这个例子里、这一次、当时”限定。

## 把个人工作流真正写进正文

用户补充自己的方法、判断或经验时，不得只写入备注。先拆清工作流，再用第一人称放进最相关案例：

1. 当前通常在哪里发生，例如飞书、钉钉、腾讯会议或本地文件。
2. 上游工具已经完成什么，例如录音、转写或基础纪要。
3. 数据怎样进入智能体：原生连接器、自定义连接器/机器人、开放接口、导出文件或手动粘贴。
4. 智能体接着做什么，例如提取议题、决定、行动项、负责人和截止时间。
5. 结果怎样回到工作流，例如追踪表、文档、邮件或项目任务。
6. 哪些内容仍需人确认，例如缺失负责人、敏感发送、权限和版本。

成片可以讲组合工作流，但必须分清：

- `product_native`：产品原生提供并已核实的能力；
- `custom_integration`：自定义连接器、机器人、MCP 或开放接口；
- `external_tool`：飞书、钉钉、腾讯会议等上游工具自己的能力；
- `manual_import`：导出、拖入、粘贴或上传；
- `creator_edit`：创作者根据选题、情绪、证据和审美进行的人工调整。

不能把五层合并成“产品已经一键全自动跑通”。当直连能力不确定时，用“能接就直接接，接不了就导出后交给它”给出可执行的降级路径。

## 自动化与创作判断

不要因为当前案例只展示脚本，就反向断言 AI 不能继续配音、剪辑、渲染或发布。先区分“案例展示到哪里”和“整条生产链还能自动化到哪里”。

合格表达应同时保留两点：

- AI 可以继续承担脚本、配音、剪辑、渲染、发布等后续动作，前提是相关工具和授权已经接通。
- 能自动化不等于成片已经有创作者的判断。钩子、情绪、证据取舍、节奏、立场和审美仍需要创作者微调；这类调整决定作品只是完整，还是有辨识度、有生命力。

不得写成“AI 只能搭结构，其他都做不了”，也不得写成“AI 已经自动完成整条链路”，除非实际证据支持。

## 流量动作与互动钩子

社媒口播默认同时设计两个不同位置、不同目的的动作，但全片仍只围绕一个内容承诺：

1. **开头动作钩子**：服务停留、收藏或后续回看。
2. **片尾评论问题**：服务讨论、需求收集和下一期选题。

开头顺序固定为“认知钩子 → 价值承诺 → 轻量动作钩子 → 正文”。第一句话必须先让观众知道为什么值得看，不能上来就说“视频比较长”“先点赞收藏”或“关注我”。长、密、工具型、清单型和可反复查询的内容，在价值承诺后优先引导收藏，并给出具体收益：以后遇到相似任务，可以回来找对应步骤或案例。

合格示例：

> 很多人知道它能干活，但真问能干什么，大多数人说不清。这期我把 11 个实践一次讲透，信息量比较大，建议先收藏，以后遇到类似任务可以直接回来查。

不合格示例：

- “这期视频比较长，大家先收藏再看。”——先暴露成本，没有先给观看价值。
- “记得点赞关注收藏转发。”——动作堆叠，没有观众收益。
- “求大家帮忙点个赞。”——乞求式互动，与内容无关。

片尾必须先完成本期结论，再提出一个具体、低门槛、能直接回答的问题。下一期尚未确定时，不编造预告，默认询问：还想看当前产品的哪个功能，或下一款想拆哪种工具；最好同时让观众写出最想解决的问题，使评论可以直接进入选题和案例研究。

合格示例：

> 还想看 WorkBuddy 的哪个功能，或者想让我拆哪款 AI 办公工具？把工具名和最想解决的问题打在评论区。

每个位置只保留一个主要动作。开头已经引导收藏，片尾就优先引导评论；不要在同一句里堆点赞、关注、收藏、转发和评论。CTA 必须由观众收益、内容争议、使用需求或下一期选择自然引出，不能像平台口令一样硬插。

## 逐句功能检查

给每个完整语义句标记至少一个功能：

- `hook`：让观众产生继续看的理由；
- `problem`：具体麻烦、代价或风险；
- `input`：要提供的材料、权限或前置条件；
- `action`：用户或产品实际做了什么；
- `state`：等待、执行、失败、空结果或完成状态；
- `result`：文件、链接、数字、任务或状态回写；
- `limit`：条件、风险、未完成或不能推出的结论；
- `judgment`：创作者的取舍与理由；
- `transition`：回答当前问题并产生下一问。
- `interaction`：给出有理由的收藏、回看或评论动作。

没有任何功能的句子通常是寒暄、同义复述、标题复读或制作说明，删除。连续三句只有 `result` 或只有 `limit` 时，检查是否变成资料播报；连续三个案例结构完全相同，检查是否变成目录陈述。

## 自然口语检查

逐句大声朗读，并执行以下规则：

- 优先“谁/什么 + 做了什么 + 得到什么”，不用名词和状态字段连续拼接。
- 一句话只承担一个主要动作或判断；并列步骤过多时拆句。
- 抽象术语出现后立即落回动作、对象或结果。
- 数字要说清它属于哪一次、哪类对象和什么状态。
- 条件与限制放在它影响的结论旁边，不集中堆到片尾免责声明。
- 允许长短句交替，避免每句长度、语气和结构完全一样。
- 如果创作者正常聊天时不会这样说，或者必须看文字才能听懂，就继续改。

重点拦截四类病句：

1. **字段腔**：“顶层文件、隐藏配置目录、下级文件夹未改动。”
2. **传话筒**：“官网给了两个场景。”
3. **幕后说明**：“这部分没有案例图片，所以视频里按文字还原。”
4. **取证报告**：“这能证明脚本结构已经生成，但不能证明后续动作已经完成。”

对应改法：

1. “这次只改了当前这一层，里面的文件夹和工具配置都没碰。”
2. “它有两个典型场景。”
3. 直接讲流程，让 MG 承担画面。
4. “脚本之后还可以继续接配音、剪辑和发布；我仍然会把钩子、情绪和证据按自己的想法再改一遍。”

## 合成前硬门禁

以下任一项未通过，不得生成完整旁白或批量制作：

- 开头不是从目标观众的信息差、好奇、焦虑或直接后果切入；
- 开头没有在认知钩子和价值承诺之后设计一个有观众收益的轻量动作钩子，或把“视频很长/先收藏”放在第一句劝退；
- 每个案例缺任务、输入、步骤、结果、限制或创作者判断中的关键一项；
- 产品选项、案例路径和创作者偏好混为一谈；
- 口播包含截图缺失、文字还原、镜头选择、制作计划或证据审计语言；
- 反复用“官网说/官网给/官网演示”作句子主语；
- 用户的个人工作流被遗漏，或被写成没有事实边界的一键原生能力；
- 把未亲测结果写成亲测，或为了避免假亲测退化成第三方资料播报；
- 把 AI 可继续自动化的动作误写成做不到，或把案例未展示的动作误写成已完成；
- 片尾没有先回收结论，再提出一个与内容相关、可以直接回答的评论问题；下一期未定却编造具体预告；
- 同一句堆叠点赞、关注、收藏、转发和评论，或 CTA 没有说明观众为什么值得行动；
- `scripts/check_audience_language.py` 返回错误；
- 全稿朗读时仍出现不自然、书面、拗口、歧义或需要回看文字才能理解的句子；
- 创作者尚未确认完整口播稿。

硬门禁通过后，再进入 TTS、字幕时码和逐句声画绑定。稿件一旦改变，旧音频、旧字幕和旧时间轴全部失效。
