# 单主智能体编排与项目状态

制作任何完整视频包时都必须读取。本文件只规定“谁负责、按什么顺序、改动后哪些结果失效”；口播、视觉、音频、字幕、封面与交付的颗粒度标准仍以各专项 reference 为准，不能因架构简化而删减。

## 一、唯一负责人

- 从 Brief、事实核验、口播、音频、时间轴、视觉导演、素材、渲染、终审到交付，始终由当前主智能体负责到底。
- 禁止把语义窗、案例、音频审核、画面审核或终验委派给子智能体，也禁止用多个独立对话分别产出后再拼接。
- 主智能体可以调用脚本、渲染器、ASR、图像生成、网页截图、媒体探测和像素检测等工具；这些工具只执行输入明确、结果可验证的确定性工作，不拥有创作判断，也不接管上下文。
- 长片可以拆成连续区间分批处理，但这是同一主智能体的内部工作清单。每个区间共用同一份 Brief、事实矩阵、术语表、时间轴、素材账本、缺陷账本和最终判断。
- 所有冲突都由主智能体依据用户已确认的方向、事实证据和实际成片解决，不能把冲突留给用户在多个版本之间拼答案。

这样做的目的不是减少质量检查，而是取消上下文反复移交。所有原有硬门槛继续执行，且只能由同一个负责人确认最终状态。

## 二、工具边界

适合交给工具的工作：

- 下载、转码、哈希、时长与编码探测；
- TTS 请求、ASR 候选、forced alignment 和静音检测；
- 按绝对时码渲染、抽帧、生成联系表和场景变化候选；
- 字幕越界、文件缺失、时间轴字段、素材来源、图文边界和发布洁净检查；
- 按明确提示生成情境图或解释素材；
- 生成审查清单与保存项目状态。

必须由主智能体亲自完成的判断：

- 口播是否符合创作者立场、事实边界和自然人话；
- 每个语义窗应选择截图、MG、生成情境还是混合表达；
- 图片是否真的证明当前句子，圈、箭头和放大是否帮助理解；
- 音色、语气、节奏、停顿和断句是否自然；
- 相邻画面是否有足够差异，整片是否连贯；
- 创作者反馈是否已经在新版实际成片中解决；
- 能否写“通过”或进入最终交付。

自动检测只能提出候选或拦截确定性错误，不能替代原尺寸看帧、连续动态播放和 `1×` 完整听审。

## 三、阶段与通过条件

项目状态固定为以下阶段：

1. `brief`：受众、核心问题、唯一结论、钩子、行动目标和视觉方向完整。
2. `evidence`：事实依据、来源、官方案例矩阵、结果与限制完整。
3. `script`：口播定稿通过自然人话、创作者立场、证据边界和互动钩子检查。
4. `audio`：最终旁白已生成或取得，原始母本、版本、哈希和听审信息可追溯。
5. `timeline`：最终音频已成为唯一主时钟，语义窗、发声锚点、字幕和音效时码完整。
6. `visual`：每窗声画合同、导演计划、对象、动作、状态和证据绑定完整。
7. `assets`：官方身份、事实证据、解释 MG、生成情境和来源记录齐全。
8. `cover`：已按专用封面 Skill 完成三比例独立构图与终验。
9. `render`：发布洁净检查通过，正式成片可完整解码。
10. `audit`：逐锚点、逐边界、动态样本、技术指标、ASR 对稿和 `1×` 完整听审均有明确结果。
11. `delivery`：最终目录只保留交付、必要源文件、事实证据和复现资料。

每个阶段只有四种状态：

- `pending`：尚未形成可检查产物；
- `current`：产物已记录，但尚未通过本阶段专项门槛；
- `approved`：主智能体已经按对应 reference 和实际产物验收；
- `stale`：上游变更后已失效，旧文件可保留作追溯，但不得继续用于生产或宣称通过。

“文件存在”“脚本运行成功”“请求已发送”“有人报告已修复”都不等于 `approved`。

## 四、依赖与失效传播

使用 `scripts/project_state.py` 记录阶段产物。任何产物内容变化都要重新计算指纹，并自动让下游状态失效：

- `brief` 变化：`evidence` 之后全部失效；
- `evidence` 变化：`script`、`audio`、`timeline`、`visual`、`assets`、`cover`、`render`、`audit`、`delivery` 失效；
- `script` 变化：`audio`、`timeline`、`visual`、`assets`、`cover`、`render`、`audit`、`delivery` 失效；
- `audio` 变化：`timeline`、`visual`、`render`、`audit`、`delivery` 失效；
- `timeline` 变化：`visual`、`render`、`audit`、`delivery` 失效；
- `visual` 变化：`assets`、`cover`、`render`、`audit`、`delivery` 失效；
- `assets` 变化：`render`、`audit`、`delivery` 失效；
- `cover` 变化：`delivery` 失效；
- `render` 变化：`audit`、`delivery` 失效；
- `audit` 变化：`delivery` 失效。

重点：

- 改口播后不能继续用旧音频；
- 改音频、删停顿或变速后不能继续用旧时码；
- 改截图裁切、标注、布局或动画后不能沿用旧逐帧验收；
- 新成片哈希与旧版不同，旧验收报告自动失效；
- 只修音频且复制视频流时，也必须生成新的成片指纹并重新完成音频、同步、技术指标和 `1×` 听审；已证明未变化的视觉项可以在报告中引用同一视频流哈希，但不能笼统沿用“整片通过”。

## 五、状态命令

初始化项目时 `scripts/init_project.py` 会同时创建 `project-state.json`。已有项目可运行：

```bash
python scripts/project_state.py init <project-dir>
```

记录一个阶段的实际产物：

```bash
python scripts/project_state.py record <project-dir> script <口播稿> --version v3
python scripts/project_state.py record <project-dir> audio <最终旁白> --version v3
```

主智能体完成该阶段专项验收后再批准：

```bash
python scripts/project_state.py approve <project-dir> script --note "朗读、立场和证据边界通过"
```

检查能否进入某个阶段：

```bash
python scripts/project_state.py check <project-dir> --through render
python scripts/project_state.py status <project-dir>
```

状态脚本只证明依赖、文件指纹和批准记录一致；它不会替主智能体观看或听审。

## 六、长片的单线程分段法

多于 24 个语义窗、时长超过约 4 分钟，或已有两类以上重复错误时：

1. 用同一时间轴生成 3–4 个连续审查区间；
2. 主智能体按时间顺序逐区间完成十二类问题表；
3. 所有问题写入同一缺陷账本，字段至少包含 `windowId`、绝对时码、问题类别、证据帧、修复动作、受影响下游阶段和复核状态；
4. 修复一个区间后重新抽取同一批锚点与边界帧，不能只看代码或修复说明；
5. 分段检查全部完成后，仍由同一主智能体从头到尾以 `1×` 完整播放；
6. 任何中途修改都按项目状态规则传播失效，再从最早失效的阶段继续。

分段只减少一次要看的画面数量，不减少上下文、问题类别、复核帧和最终完整播放。

## 七、完成定义

只有以下条件同时成立才能把 `delivery` 标记为 `approved`：

- 所有上游阶段均为 `approved`，没有 `stale`；
- 最终成片、封面、口播、字幕、发布包和验收报告对应同一版本；
- 逐锚点和边界复核针对最终成片哈希，而不是旧版本；
- 技术检测、画面终审、ASR 对稿、音频听审和创作者反馈分别有结论；
- 项目清理后重新列目录并复验保留的最终文件；
- 未获发布授权时只交付，不上传或发布。
